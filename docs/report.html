Лабораторная работа №9. REST API на PHP / Laravel 11, СУБД MySQL 8.4.

Выбранная диаграмма — классов

Диаграмма классов отражает сущности предметной области, их атрибуты, методы связей Eloquent и кратности. Она подходит для проектирования базы данных и моделей API. Отдельные диаграммы других видов не используются.

Связи: отдел имеет минимум одну продажу; товар может не иметь продаж. Каждая продажа обязательно относится ровно к одному отделу и одному товару. Внешние ключи не допускают NULL. PK — первичный ключ, FK — внешний ключ, UQ — уникальное значение.

Принятые решения

Код отдела и артикул товара — уникальные бизнес-идентификаторы; внутренние id служат для связей. daily_plan трактуется как дневной план в рублях. Это допущение позволяет сравнивать план с фактической выручкой. План считается постоянным: изменение daily_plan влияет и на отчёты за прошлые даты. Для исторических планов потребуется отдельная таблица планов по датам.

Одна продажа содержит один вид товара. Количество может быть дробным (до трёх знаков), цены — с двумя знаками. unit_price сохраняет текущую розничную цену при регистрации продажи; при смене товара в продаже цена обновляется. Пользователь не задаёт unit_price вручную. Выручка вычисляется как сумма округлённых до копеек произведений количества и сохранённой цены.

Отдел создаётся атомарно с initial_sale. Последнюю продажу отдела нельзя удалить или перенести. Связанные отделы и товары защищены от удаления (409). Все изменения API выполняются в транзакциях с общей блокировкой trade_locks: это простой способ исключить гонки для учебного проекта; при высокой нагрузке его следует заменить более детальными блокировками. FK и CHECK обеспечивают ссылочную целостность и диапазоны в MySQL. Обязательное наличие продажи у отдела обеспечивает приложение: прямой SQL в обход API может нарушить это правило.

«Ежедневно несколько продаж» рассматривается как описание деятельности, а не ограничение минимум две записи на каждую календарную дату: требование не задаёт рабочий календарь. Кратность 1..* реализует явно заданное обязательное участие отдела в продажах.

API

Метод и адресНазначение
GET /api/{entity}Список, пагинация по 25 записей, параметр page
POST /api/{entity}Создание (201)
GET /api/{entity}/{id}Просмотр (200)
PUT / PATCH /api/{entity}/{id}Полная / частичная замена (200)
DELETE /api/{entity}/{id}Удаление (204 без тела)
GET /api/reports/daily?date=2026-05-01План, выручка, отклонение и процент по каждому отделу. При плане 0 процент равен null.
GET /api/reports/demand?from=2026-05-01&to=2026-05-31Количество, выручка и число продаж каждого товара за включительный период. Порядок по числу продаж убыванию, затем id.

entity: departments, products, sales. Показатель спроса — число записей продаж: количества разных единиц измерения нельзя корректно сравнивать напрямую. Товары без продаж включены с нулевыми показателями. Отчёт спроса возвращает весь каталог без пагинации.

Ошибки: 404 — запись не найдена, 422 — неверные поля, 409 — нарушение бизнес-правила. API возвращает JSON. FormRequest проверяет входные данные, контроллер применяет бизнес-правила, Repository изолирует CRUD, Eloquent работает с MySQL, Resource формирует выдачу.

Запуск и проверка

См. START.txt и requests.http. Исходник этой же диаграммы: classes.puml.

API предназначен для лабораторной работы и запуска на localhost. Авторизация в объём задания не включена.

Реализация сверена с официальными разделами Laravel 11: Routing и Validation.
